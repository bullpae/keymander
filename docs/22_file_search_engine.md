# 22. 파일 검색 엔진 — 수십만 개를 세 OS에서 똑같이 빠르게

> 상태: **설계 v4.1, F0 출시(v0.18.1)·F1·F2 구현** (2026-10-26, 브랜치 `bullpae/filesearch-f1`·`-f2`) — **IPC 없는 내장 검색 + 불변 스냅숏(mmap) + 변경분 세그먼트**.
> v1~v3.1 은 "데몬이 색인을 들고 런처가 IPC 로 묻는" 구조였다. 보안·차단 환경 검토 끝에 파일 검색에서 IPC 를 뺐다(§7).
> 계기: Windows 10 사용자 보고 — `:scope` 로 `E:\MyOffice` (파일 약 40만, 폴더 약 8,200)를 넣었더니
> `2022년` 이후 폴더가 검색되지 않음. 직접 원인은 커밋 08ed07c 에서 고쳤다(§2.1). 이 문서는 근본 구조를 다룬다.
> 관련: [18_search_scope_ux.md](18_search_scope_ux.md)(`:scope`), [15_content_search_plan.md](15_content_search_plan.md)(본문 검색, FTS5 — 범위 밖)

## 1. 목표

| | 목표 |
|---|---|
| 규모 | 검색 범위 안 파일 **100만 개**까지 할당량 없이 색인 (안전 상한 `max_files` 만) |
| 런처 시작 | 색인 크기와 무관 — 런처는 스냅숏을 **역직렬화하지 않고 매핑만** 한다 (측정 0.05~0.15ms) |
| 키 입력 → 결과 | 런처 안 검색 **p95 5ms** (40만, 4스레드). 질의 종류별로 따로 잰다 |
| 정확성 | 결과가 덜 나오거나 이전 질의 결과가 남는 일이 없다 |
| 신선도 | 로컬 NTFS·APFS·ext4: 데몬 동작 중 = **수 초**(감시), 데몬 없어도 = **런처를 여는 순간**(열 때 대조, §3.8). FAT·네트워크는 주기 재나열, 상태로 표시 |
| 보안 | 파일 검색에 **접속 창구(포트·파이프·소켓)를 만들지 않는다**. 색인 파일은 현재 사용자만 |
| 이식성 | 세 OS 같은 코드. Everything·Spotlight 는 선택 가속 |
| 자원 | 스냅숏 40만 ≈ 40MB(디스크·페이지 캐시 공유). 인덱서는 키 훅을 굶기지 않는다(2026-08-08 수칙) |

**하지 않는 것**: 본문 검색(docs/15), 범위 밖 디스크 전체 검색(Everything 영역), MFT 직접 읽기(관리자 권한), 원격 검색.

## 2. 지금 구조와 문제

### 2.1 구조

```
데몬: 6시간마다 Index::build → index.bin + index.json, 자기 SearchEngine(Mutex) 갱신
런처(단축키마다 데몬이 새 프로세스로 띄움, server.rs:1010): quick-index.bin → 표시 → index.bin → SearchEngine(nucleo) 구성
검색: update 안에서 동기 호출 (search_routing.rs:296) → 모드 판정 → 결과 → frecency 가중(:319)
IPC: 127.0.0.1 TCP + 토큰 (ipc.rs:5-11), 연결 하나에 요청 하나 — 클립보드·키 주입·상태 등에 사용, 파일 검색에는 미사용
```

- 파일 수집: `collect_priority_files`(walkdir 단일 스레드) + 일반 프로바이더가 남은 할당량을 채움. 상한 `launcher.max_results` 기본 5000.
- 08ed07c: 폴더는 할당량 밖(5만까지), 파일 몫은 검색 폴더별로 나누고 얕은·최근 우선. **파일 상한은 남아 있다.**

### 2.2 측정과 문제 (M 시리즈, release, 합성 항목)

| 항목 수 | index.bin | 로드 | `SearchEngine::with_items` | 한 글자 | "보고서 최종"(contains) |
|---|---|---|---|---|---|
| 5천 | 1MB | 1ms | 13ms | 1ms | 3ms |
| 5만 | 10MB | 9ms | 61ms | 2ms | 24ms |
| 40만 | 79MB | 79ms | 494ms | 11ms | 188ms |

1. **런처 시작 비용이 색인 크기에 비례** — 40만이면 창마다 +0.57초(로드 + 엔진 구성).
2. **결과 누락** — `search_fuzzy` 가 `nucleo.tick(10)` 을 한 번만 부른다(search.rs:297). 40만에서 `2` → 0건, 이어 `zzzz` → 이전 결과 50건.
3. **contains 가 느리다** — 항목마다 경로 조각 `HashSet` 을 새로 만든다(search.rs:402).
4. **점수가 품질이 아니다** — 퍼지 점수는 순위 `(count−i)*10`(search.rs:308)이라 kind 가중(폴더 80·앱 70, types.rs:359)이 매칭 품질을 압도.
5. **항목이 무겁다** — 경로를 `path`·`keywords` 에 두 번, 아이콘 문자열까지(≈130~200B/항목).

### 2.3 새 구조 시제품 측정

`scratchpad/soa/` (40만 항목, 이름+오프셋+부모 16.5MB):

| | 결과 |
|---|---|
| 메모리 내 순서일치 거르기, 18스레드 | 0.6~1ms, 이어 치기 좁히기 0.2~0.5ms |
| **새 프로세스에서 스냅숏 열기 + mmap** | **0.05~0.15ms** |
| **mmap 직후 첫 검색, 4스레드** (페이지 폴트 포함, 페이지 캐시 warm) | **1.1~2.3ms** |

재부팅 직후(디스크 콜드)는 16~40MB 를 한 번 읽어야 한다 — SSD 수십 ms, HDD 더. 인덱서가 막 쓴 파일이라 보통 캐시에 있다. Windows·4코어 실측은 F1.

| 도구 | 방식 |

| Everything | MFT 적재, 서비스가 이름 배열 + 부모 참조를 상주, USN 저널 갱신, IPC 질의 |

100만 이하에서는 역색인보다 캐시 친화적 선형 스캔이 단순하고 빠르다.

## 3. 설계

### 3.1 한눈에

```
┌──────────── 인덱서 (데몬 안, 또는 데몬 없으면 런처 백그라운드) ────────────┐
│ Scanner(첫 스캔) ─▶ FileTable(메모리) ◀─ Dirty 큐 ◀─ notify·mtime 대조·재스캔 │
│                         │                                                 │
│                    Publisher: base.<gen>.snap  +  delta.<gen>.<seq>.seg    │
│                               └─ manifest (현재 base·delta 목록, 원자적 교체)│
└─────────────────────────┬─────────────────────────────────────────────────┘
                          │  파일만 (사용자 전용 디렉터리)
┌──────────── 런처 (단축키마다 새 프로세스) ──────────────────────────────────┐
│ manifest 읽기 → base·delta 읽기 전용 mmap → LogicalView(base − tombstone + delta)│
│ 키 입력 → Query(거르기 → 싼 점수 → Matcher → rank::combine, frecency 는 런처 자신의 것) │
│ quick-index(앱·명령·최근)와 같은 점수 척도로 합쳐 표시                          │
└──────────────────────────────────────────────────────────────────────────┘
```

- **검색 요청은 프로세스 경계를 넘지 않는다.** 런처가 같은 프로세스에서 검색 코어를 함수로 부른다.
- 인덱서와 런처 사이의 계약은 **파일 형식과 manifest** 뿐이다.
- v3 의 IPC 쪽 숙제(비동기 수신, request_id, 연결 유지, 데몬·런처 버전 협상, 막혔을 때 전환)가 파일 검색에서 사라진다.

### 3.2 크레이트 구성

```
crates/kmd-core/src/filesearch/   (처음엔 kmd-core 모듈, 커지면 별도 크레이트)
  table.rs      FileTable(쓰기용, 메모리) · View(읽기용, 매핑된 바이트 위)
  snapshot.rs   base 형식: 쓰기·검증·mmap 열기
  delta.rs      변경분 세그먼트 형식
  manifest.rs   현재 세대 목록, 원자적 교체·정리
  query.rs      모드별 거르기·폴더 마스크·싼 점수·Matcher
  rank.rs       rank::combine (quick-index·파일 공용)
  index/        scanner.rs · watcher.rs · reconciler.rs · publisher.rs  (OS 어댑터는 여기만)
```

`table`·`snapshot`·`delta`·`query`·`rank` 는 OS·IPC 에 의존하지 않는다.

### 3.3 FileTable — 구조 배열

```rust
// 스냅숏의 열과 1:1. 쓰기 쪽(인덱서)은 Vec, 읽기 쪽(런처)은 매핑된 &[T]
struct Columns {
    raw: [u8],            // 원본 이름 바이트 (Unix: OsStr 바이트, Windows: WTF-8) — 경로 복원은 이것으로만
    raw_off: [u32],
    folded: [u8],         // 검색용: NFC + 소문자. 이름 사이 구분 바이트 0x00
    folded_off: [u32],    // 접으면 길이가 변한다(İ, K 기호, NFD→NFC) → 오프셋 따로
    parent: [u32],        // 부모 폴더 행 (루트 u32::MAX)
    root_id: [u16],       // 행이 속한 검색 폴더
    bag: [u64],           // 문자 가방: ASCII 영숫자 36비트 + 한글 초성 19비트 + 기타
    meta: [u32],          // kind 2bit·깊이·확장자 id·숨김·삭제·클라우드 자리표시자
    mtime: [i64],         // 전체 해상도
}
// 인덱서 메모리 전용 (스냅숏에는 폴더 것만): dir_ids: HashMap<(vol, file_id), row>
```

- **원본과 검색용 분리**: NFC 로 바꿔 저장하면 ext4·SMB 에서 맥발 NFD 이름을 못 열고, Windows 의 짝 없는 서로게이트는 UTF-8 로 못 담는다.
- **전체 경로는 저장하지 않는다.** 결과 상위 N개만 `parent` 를 따라 복원.
- 40만: raw·folded 각 ~14MB + 나머지 ~10MB ≈ 38MB.
- **행 수명**: 행 번호가 id 이자 `parent` 참조. **재사용하지 않는다**(재사용하면 정리 안 된 자식이 엉뚱한 폴더 밑으로 간다).
  삭제는 tombstone, 새 행은 뒤에. 삭제가 쌓이면 새 base 를 만들면서 행 번호를 다시 매긴다(= 압축).
- 기존 `search_depth`(기본 4)는 검색 폴더별 깊이 상한으로 유지.

### 3.4 스냅숏 · 변경분 · manifest

**base 스냅숏** `base.<gen>.snap` — 불변, 한 번 쓰고 다시 고치지 않는다.

```
[헤더 64B] magic "KMDFS" · 형식 버전 · gen · 행 수 · 열 개수 · 플래그 · 헤더 체크섬
[열 목차]  열마다 (종류, 오프셋, 길이, 원소 크기, 체크섬)   — 오프셋은 8바이트 정렬
[열 데이터] raw · raw_off · folded · folded_off · parent · root_id · bag · meta · mtime
[루트 표]  검색 폴더 경로(원본 바이트)·볼륨 종류·상태·스캔 시각
```

**변경분 세그먼트** `delta.<gen>.<seq>.seg` — 역시 불변, 작다(수 KB~수 MB).

- 추가 행: base 와 같은 열 형식, 행 번호는 `base 행 수 + 누적 추가 수` 부터.
- tombstone: 지운 행 번호 목록(정렬).
- 바뀐 행: 이름 변경·이동 = tombstone + 추가로 표현(단순함 우선). 폴더 이동은 예외 — 아래.
- 폴더 이동(`dir_ids` 로 같은 폴더임을 확인한 경우): `(row, new_parent, new_name)` 재배치 레코드. 하위 수천 개를 다시 쓰지 않는다.

**manifest** `files.manifest` — 현재 읽을 것: `base gen` + `delta seq 목록` + 체크섬.

- 인덱서는 새 파일을 **같은 디렉터리에 임시 이름으로 `create_new`** → 다 쓰고 flush → 최종 이름으로 rename → 새 manifest 를 같은 방식으로 쓰고 rename 으로 교체.
- 런처는 시작 시 manifest 를 읽고 그 목록만 연다. 열린 동안 manifest 가 바뀌면(파일 mtime 확인, 키 입력 사이에) 새 목록으로 다시 연다.
- **고친 파일을 매핑하는 일은 없다** — Unix 의 덮어쓰기·truncate SIGBUS, Windows 의 매핑 중 rename 금지를 모두 피한다.
- 옛 세대 정리: manifest 에서 빠진 지 일정 시간(기본 10분) 지난 파일을 인덱서가 지운다. Windows 에서 아직 매핑 중이라 지우기가 실패하면 다음 정리 때 다시.
- 변경분이 base 의 일정 비율(예: 5%) 또는 개수(예: 64)를 넘으면 인덱서가 백그라운드에서 새 base 를 만들고 manifest 를 교체.

**변경분 공개 주기**: 변경 묶음(debounce 500ms~1s)마다 세그먼트 하나. 그래서 로컬 디스크 신선도가 "수 초".

### 3.5 읽기 — LogicalView

- `View` = base 매핑 + delta 매핑들. 질의는 base 행을 훑되 tombstone 비트셋(세그먼트들에서 모아 런처 시작 시 한 번 구성)을 건너뛰고, delta 추가 행을 이어서 훑는다.
- 재배치 레코드는 `parent`·이름 덮어쓰기 맵(작음)으로 적용.
- **스냅숏은 신뢰하지 않는 입력으로 다룬다**: 열기 시 헤더·목차 체크섬, 열 길이 일관성, 모든 `off` 단조 증가·범위 안, `parent < 행 수` 를 검증. 실패하면 그 세대를 버리고 이전 세대 또는 옛 경로로.
  열 데이터 전체 체크섬은 인덱서가 쓸 때 계산하고, 런처는 헤더·목차만 검사(전체 해시는 매번 16MB 를 읽게 된다).
- 바이트를 `&[u32]` 로 볼 때 정렬·엔디언(리틀 엔디언 고정, 빅 엔디언 기계는 미지원 표시)을 확인. `unsafe` 는 `snapshot.rs` 한 곳에 모은다.

### 3.6 질의

질의는 `SearchMode::detect` 를 그대로 쓰고, 토큰을 공백으로 나눈다.

**거르기 (모드별)**

| 토큰 | 방법 |
|---|---|
| 비ASCII(한글 등) | `folded` 블롭 **전체**에 `memchr::memmem::Finder` 한 번 → 히트 오프셋을 `folded_off.partition_point` 로 행으로 |
| ASCII, 3글자 이상 | `bag` AND 로 먼저 거름 → 남은 것만 subsequence |
| ASCII, 1~2글자 | **별도 경로**: 접두·단어 시작 일치만 후보로 (subsequence 로는 `2` 가 27만 개 통과) |
| glob·확장자 | 확장자 id 비교 → 패턴 |
| regex | 크기 상한(search.rs:341 유지) + 후보 상한 선형 스캔 |

- 혼합 질의(`2026 보고`)의 비ASCII 토큰은 바이트 subsequence 로 돌리지 않는다(UTF-8 연속 바이트 교차 매칭).
- **여러 토큰·경로 질의**: 토큰마다 **폴더만** 먼저 매칭해 `folder_mask` 를 만들고 `anc_mask[f] = folder_mask[f] | anc_mask[parent[f]]` 로 전파. 파일은 `(own | anc_mask[parent]) == ALL` 한 번. O(폴더×토큰 + 파일).
- 실행: 런처 프로세스의 작은 스레드 풀(코어/2, 최대 4). 런처는 키 훅을 갖지 않으므로 데몬보다 여유가 있지만, 질의마다 스레드를 띄우지는 않는다.

**점수**

1. 후보가 5천을 넘으면 **모든 후보**에 싼 점수(정확·접두·단어 시작·이름 길이·frecency 유무)를 매겨 상위 5천을 `select_nth_unstable`. 먼저 발견된 순서로 자르지 않는다.
2. 그 안에서만 nucleo `Matcher`(`Nucleo` 워커·tick 미사용 → §2.2-2 구조적 해소). **거르기는 Matcher 의 상위 집합**이어야 한다.
3. `rank::combine`(§3.7) → 상위 `limit`.

**이어 치기 좁히기**(측정 후 결정): fuzzy·contains 에서만, 이전 질의의 확장이고 View·모드가 같을 때만.

검색은 런처 안 함수 호출이라 동기여도 된다(수 ms). 다만 10ms 를 넘는 질의(regex 등)는 지금 `:c` 처럼 Task 로 돌리고, 결과에 질의 번호를 붙여 늦게 온 것은 버린다.

### 3.7 순위 — 한 곳에서

```
final = match   (0..100 nucleo 정규화; 정확 +40, 접두 +25, 단어 시작 +15)
      + where   (이름에서 매칭 ×1.0, 조상 폴더에서만 ×0.6)
      + kind    (앱 +20, 폴더 +15, 파일 0)        ← 정확 일치보다 작게
      + frecency(최대 40)
      + recency (mtime 1일 +15, 1주 +10, 1달 +5)
      − depth   (검색 루트 아래 단계당 2, 최대 10)
동점: 이름 짧은 순 → 최근 수정 순
```

- **frecency 는 런처가 이미 갖고 있다**(history.rs) — 검색이 런처 안이라 v2~v3 의 "데몬이 history DB 를 읽어야 하나" 문제가 없다.
  frecency 상위 경로는 행 번호로 미리 찾아 두고, 싼 점수 단계부터 반영해 상위 K 밖으로 밀리지 않게 한다.
- quick-index 결과와 파일 결과를 같은 `rank::combine` 으로 합친다. `boost_results_with_map` 은 이것으로 대체.
- 바꾸기 전에 실사용 이력으로 **골든 셋**("질의 → 기대 1위")을 만든다. 앱·PATH 순서도 바뀌므로 필수.

### 3.8 인덱서 — 누가, 어디서

| 상황 | 인덱서 |
|---|---|
| 데몬 동작 중 (기본) | **데몬 안의 스레드**. 상주하므로 감시·대조·공개를 계속 |
| 데몬 없음 / 꺼둠 / 실행이 막힘 | **열 때 대조**: 런처가 창을 띄우자마자 백그라운드 스레드에서 스냅숏의 폴더 행 mtime 을 전부 확인(아래 측정) → 바뀐 폴더만 재나열 → **메모리 변경분으로 이번 검색에 바로 반영** + 세그먼트로 공개해 다음 런처도 쓴다. 감시는 없지만 사용자가 검색하는 순간(= 런처를 연 순간)의 상태를 본다 |
| 둘 다 안 됨 (쓰기 금지 등) | 읽기만, 상태 줄에 "색인 n분 전" |

- **열 때 대조 비용**(macOS, 실제 폴더 2만 개 mtime 확인): 1스레드 32~95ms, **4스레드 11ms**. 폴더 8,200개면 약 5ms. Windows NTFS 는 F1 에서 실측(몇 배 느려도 백그라운드라 창 표시를 막지 않는다).
  첫 키 입력 전에 끝나는 경우가 대부분이고, 늦으면 끝난 뒤 결과를 한 번 갱신한다. FAT·네트워크 루트는 폴더 mtime 을 믿을 수 없어 열 때 대조에서 빼고 주기 재나열.
  데몬이 동작 중이어도 감시가 놓친 경우(버퍼 넘침 직후 등)의 보조로 쓸 수 있다 — 데몬이 `files.lock` 을 잡고 있으면 런처는 읽기 전용으로 대조만 하고 공개는 데몬에 맡긴다.
- 인덱서는 한 번에 하나: manifest 옆의 잠금 파일(`files.lock`, flock / `LockFileEx`). 데몬이 잡고 있으면 런처는 인덱싱하지 않는다.
- 스캔·대조 스레드는 상한(코어/2)과 낮은 우선순위(macOS QoS utility, Windows background mode, Linux nice).
- **OneDrive 등 클라우드 자리표시자**: 나열만 하고 열지 않는다(하이드레이션 유발). 내려받지 않은 폴더는 내려가지 않는 옵션.

### 3.9 갱신

볼륨 종류를 먼저 판별한다(`GetVolumeInformationW`·`statfs`).

| 볼륨 | 방법 |
|---|---|
| NTFS·ReFS·APFS·HFS+·ext4·btrfs (로컬) | `notify` 변경 알림 + 폴더 mtime 대조 안전망 |
| FAT32·exFAT | 폴더 mtime 이 하위 변경에 갱신되지 않음 → 알림 + 주기 재나열 |
| SMB·NFS | 디렉터리 캐시(SMB ~10초, NFS ~30초) → 주기 재나열, 알림은 보조 |
| 외장 HDD | 콜드 stat 이 디스크를 깨움 → 알림 오버플로·절전 복귀 때만 대조 |

**이벤트는 "변경 목록"이 아니라 "여기는 더 이상 믿을 수 없다"는 신호로 다룬다.**

```
OS 감시(notify) ─┐
mtime 대조 ──────┼─▶ 정규화 ─▶ Dirty 큐 ─▶ 대조기 ─▶ FileTable 변경 ─▶ 세그먼트 공개
절전 복귀·재연결 ─┤              ├ DirtyEntry   : 그 폴더 한 단계 재나열
분할 재스캔 ─────┘              ├ DirtySubtree : 폴더와 하위 전부 (새 폴더, MustScanSubDirs, 대량 이동)
                                └ DirtyRoot    : 루트 전체 검증 (버퍼 넘침, 감시 재설정)
```

- 같은 폴더 이벤트는 합치고, 하위 Dirty 는 상위 Subtree 에 흡수, 큐가 넘치면 Root 로 격상.
- 폴더 이동은 `dir_ids` 로 같은 폴더임을 확인하면 재배치 레코드 하나. 확인 못 하면 옛 트리 tombstone + 새 트리 스캔.
- 대소문자만 바꾼 이름 변경은 `raw` 로 비교. 대소문자 구분 FS 에서 접힌 키로 중복 제거하지 않는다.
- 버퍼 넘침(Windows `ERROR_NOTIFY_ENUM_DIR`, notify `Rescan`)·FSEvents `MustScanSubDirs`·절전 복귀·볼륨 재연결(볼륨 시리얼 확인) → Subtree/Root.
- inotify `max_user_watches` 한도(구 커널 8,192) 초과 → 주기 재나열로 동작하고 상태에 표시.
- Windows 재귀 감시는 루트 핸들을 열어 두어 외장 디스크 꺼내기를 막는다 → 볼륨 제거 알림에 감시 해제.
- 본문 색인 감시(`spawn_content_watcher`, server.rs:389)와 감시자를 공유.
- 폴더 mtime 대조는 mtime(전체 해상도)+항목 수 비교. 최종 안전망은 유휴 시 분할 전체 재스캔(하루 한 바퀴).
- **데몬 시작 순서**: manifest 로드 → **감시 먼저 등록** → 루트별 대조(꺼져 있던 동안의 변경).
- **외장 디스크 분리**: 색인을 지우지 않고 루트를 오프라인 표시(결과에 흐리게), 재연결 시 볼륨 시리얼이 같으면 대조, 다르면 재스캔.
- **신선도 두 등급**: 로컬·감시 정상 = 수 초. 감시 불가·원격·오프라인·데몬 없음 = 주기만큼, `kmd index --stats` 와 `:scope` 에 루트별 상태.

### 3.12 보안

**신뢰 경계는 같은 사용자 계정이다.** 같은 계정의 악성 프로그램은 색인 파일도 디스크도 직접 읽을 수 있으므로 그것을 막는다고 주장하지 않는다.
목표: (1) 다른 계정·다른 PC·웹 페이지가 닿을 창구를 만들지 않는다, (2) 색인 파일이 새는 경로를 만들지 않는다, (3) 변조된 색인이 런처를 깨뜨리지 못한다.

| ID | 요구사항 | 단계 |
|---|---|---|
| SEC-01 | **파일 검색에 접속 창구 없음** — 포트·파이프·소켓을 열지 않는다. 인덱서→런처는 파일만 | F1 |
| SEC-02 | 인덱서는 **일반 사용자 권한**으로만. 관리자로 실행되면 경고하고 파일 색인을 하지 않는다(다른 프로필 파일 이름 노출 방지) | F1 |
| SEC-03 | 색인 디렉터리: `LocalAppData`(Windows — Roaming 은 도메인 로밍 프로필로 서버에 동기화될 수 있다)·`~/Library/Application Support`·`$XDG_DATA_HOME`. Unix 디렉터리 0700·파일 0600, Windows 는 사용자 프로필 ACL. 디렉터리 소유자가 현재 사용자가 아니면 쓰지도 읽지도 않는다. 포터블 모드여도 색인은 포터블 폴더(USB 등)에 두지 않는다 | F1 |
| SEC-04 | 쓰기: 임시 이름 `create_new`(Unix `O_NOFOLLOW`, 심볼릭 링크 바꿔치기 방지) → rename. 읽기: 읽기 전용 매핑 | F1 |
| SEC-05 | **스냅숏은 신뢰하지 않는 입력** — 헤더·목차 체크섬, 오프셋·`parent` 범위 검증(§3.5). 퍼징 대상 | F1 |
| SEC-06 | 질의·경로를 로그에 남기지 않는다(길이·개수만). 읽지 못한 폴더는 "n개" 만 | F1 |
| SEC-07 | 진단: `kmd index --stats` 에 세대·신선도·루트 상태·인덱서 위치(데몬/런처/없음) | F2 |
| SEC-08 | 테스트: 손상·잘린·버전 다른·심볼릭 링크로 바꿔치기된 스냅숏, 거대한 길이 필드, 순환 `parent` | F1·F3 |

**기존 IPC (파일 검색과 별개)** — 클립보드·키 주입·상태용 TCP+토큰은 남는다. 점검에서 찾은 것:

- 같은 토큰으로 키 주입(`InjectPaste`·`PasteEnter`·`EnterOnly`)·클립보드 기록(`ClipHistory`)·위치(`Location`)·URL 열기(`LlmAutopilot`)가 된다.
- **`LlmAutopilot` 의 `url` 을 데몬이 검사하지 않는다** — http(s) 가 아니면 Windows 에서 `explorer.exe <경로>` 로 연다(action.rs:95-111). IPC 로 임의 파일 실행이 가능하다 → F0 에서 `https://` 만 받게 고친다.
- 후속: 데몬이 런처를 띄울 때(server.rs:1010) **상속되는 익명 채널**(Unix socketpair, Windows 상속 익명 파이프)을 넘겨 런처↔데몬 통신을 옮기면 이름·포트·토큰 파일이 없어진다.
  사용자가 런처를 직접 띄운 경우만 TCP 로 남기거나 그 기능을 끈다. 별도 문서로.

### 3.13 차단된 환경

| 막힌 것 | 동작 |
|---|---|
| 로컬 TCP·IPC (EDR·DLP·방화벽 정책) | **파일 검색은 영향 없음.** 클립보드 기록 등 IPC 기능만 꺼짐 |
| 데몬 실행 (애플리케이션 제어) | 런처가 인덱서 역할(§3.8) — 감시 없이 주기 대조 |
| 파일 감시 API | 주기 대조로 동작, 상태 표시 |
| 색인 디렉터리 쓰기 | 읽기만 / 옛 경로(`index.bin`)로 |
| 특정 폴더 접근 | 건너뛰고 "읽지 못한 폴더 n개" |

엄격한 보안 PC 에서 모든 기능이 동작한다고 보장하지 않는다. 막힌 것은 상태로 보여 주고, 막혔다고 다른 방법으로 몰래 우회하지 않는다.

### 3.14 호환성 정책

| 항목 | 정책 |
|---|---|
| 심볼릭 링크·정션 | 따라가지 않는다(`follow_links(false)`). 순환·중복 방지 |
| 중첩 scope | 같은 경로를 두 번 색인하지 않는다(`covering_root` + 루트 간 중복 제거) |
| 대소문자 | 검색은 접은 이름, 같은 파일 판단은 FS 의미론(원본 이름·id) |
| 권한 없는 폴더 | 건너뛰고 "n개" 기록 |
| 외장 디스크 | 분리 시 오프라인 표시, 색인 보존 |
| 네트워크 경로 | UNC·SMB·NFS 는 폴링 등급 |
| macOS 앱 번들 | `.app` 하나, 안으로 내려가지 않음(docs/18 §9) |
| `max_files` 초과 | 얕은·최근 우선(08ed07c 규칙) + **"색인 불완전 — n개 빠짐"** 표시 |
| 빅 엔디언 | 스냅숏은 리틀 엔디언 고정, 빅 엔디언 기계는 옛 경로 |

### 3.15 설정

```toml
[launcher.file_search]
engine = "auto"          # auto(새 엔진, 실패 시 옛 경로) | legacy
indexer = "auto"         # auto(데몬, 없으면 런처) | daemon | launcher | off
max_files = 1000000
stale_minutes = 10       # 런처 인덱서가 대조를 시작하는 manifest 나이
accelerator = "none"     # none | everything (F4)
```

## 5. 테스트

- **참조 구현 차등(proptest)**: 현 엔진은 tick 문제가 있어 정답으로 삼지 않는다. 느리지만 확실한 참조 구현(전 항목에 Matcher·contains 직접 적용)과 비교. 한글·NFD·대소문자·서로게이트 섞인 이름 무작위 생성. contains·glob·regex 는 결과 집합이 같아야 하고, 퍼지는 후보 ⊇ Matcher 매칭.
- **스냅숏 퍼징(cargo-fuzz)**: 임의 바이트·잘린 파일·거대 길이·순환 `parent` 를 열어도 패닉·범위 밖 읽기 없이 거절.
- **경로 복원**: 원본 이름 → 경로가 원래 경로와 바이트 단위로 같다(서로게이트·NFD 포함).
- **상태 전이**: base+delta 결과 = 같은 내용으로 새로 만든 base 결과, 폴더 통째 이동, 대량 삭제 후 추가 → 압축 뒤 `parent` 무결성, 버퍼 넘침 → 완전 복구, 인덱서 강제 종료(쓰다 만 임시 파일) → 이전 세대로 정상 검색, 런처가 옛 세대를 매핑 중일 때 정리, 외장 디스크 분리·재연결, 중첩 scope, 권한 없는 폴더.
- **벤치**: CI 는 명령어 수(iai-callgrind)로 회귀만. 시간은 로컬·Windows 실기에서 1·2·4·8 스레드, 질의 종류(1~2글자·일반·경로·한글·regex)별 p95, 콜드(재부팅 직후)·warm 따로, 40만·100만 따로.

## 6. 위험

1. **1~2글자 후보 폭발**(27만) — 별도 경로와 후보 상한이 없으면 5ms 가 무너진다.
2. **콜드 첫 검색** — 재부팅 직후 첫 런처는 스냅숏을 디스크에서 읽는다(HDD 면 수백 ms 가능). 데몬이 시작할 때 base 를 한 번 훑어 캐시에 올려 두는 선읽기 검토.
3. **볼륨별 갱신 차이** — 판별 없이 mtime 대조만 믿으면 FAT·SMB 에서 "지웠는데 남는" 결과.
4. **스냅숏 형식 고정** — 런처·데몬 버전이 다르면(채널이 여럿) 형식 버전이 안 맞을 수 있다 → 버전 다르면 옛 경로, 인덱서가 새 버전으로 다시 씀.
5. **순위 전면 교체** — 골든 셋 없이는 회귀를 못 본다.

## 7. 검토 이력 (2026-10-26)

- **v1 → v2** (Claude Fable 5.1·Opus 5.5 읽기 전용 검토): IPC 실체(TCP+토큰) 정정, 1~2글자 후보 폭발·싼 점수·후보 상한, 원본 이름 보존·오프셋 분리, 볼륨별 갱신, 폴더 이동은 한 칸 교체, notify 함정, 문자 가방·폴더 마스크, 현 점수가 순위라 kind 가중이 품질을 압도, 런처 동기 검색의 UI 멈춤, OneDrive 자리표시자, 참조 구현·퍼징 테스트.
- **v2 → v3** (GPT Astra): 행 재사용 금지·tombstone·압축, `root_id`, 변경마다 전체 복제 금지(불변 base + 변경분), 싼 점수는 모든 후보에, Dirty 큐 격상, 시작 시 감시 먼저, 신선도 두 등급, 호환성 표, F0 완료 조건, 할당량 제거는 갱신 검증 뒤.
- **v3 → v3.1** (GPT Astra 보안): SEC 요구사항, 정책으로 꺼짐 vs 실패 구분·몰래 우회 금지. 점검 중 `LlmAutopilot` URL 미검증 발견.
- **v3.1 → v4** (사용자 질문 "IPC 말고 안전한 방법" + 다른 모델의 대안 검토): **파일 검색에서 IPC 를 뺐다.**
  - 근거: 접속 창구가 없어지고(SEC-01), 로컬 TCP 를 막는 보안 제품의 영향을 받지 않으며, 데몬이 없어도 같은 품질로 검색되고,
    frecency 가 런처에 있어 점수 위치 문제가 사라지며, v3 의 IPC 숙제(비동기·request_id·연결 유지·버전 협상·전환 규칙)가 없어진다.
  - 비용: 런처가 스냅숏을 직접 읽는다 — 측정상 매핑 0.05~0.15ms, 첫 검색 1.1~2.3ms(warm). 콜드는 위험 2.
  - v2 검토에서 두 모델은 "IPC 기본, mmap 은 폴백"을 권했다. 그 이유(Windows 매핑 파일 교체, SIGBUS, 변경마다 30MB 재작성)는
    **불변 세대 파일 + 작은 변경분 세그먼트 + manifest**(§3.4)로 해소된다 — 고친 파일을 매핑하는 일이 없다.
  - SQLite 는 쓰지 않는다: 파일 이름 퍼지 Top-K 에는 행을 많이 읽게 되고, WAL 도 파일 잠금·공유 메모리를 쓴다. 본문 검색(FTS5)·이력은 지금처럼 SQLite.
  - 공유 메모리는 쓰지 않는다: 권한·동기화 부담만 늘고 파일 mmap 보다 나을 게 없다.
- **v4 → v4.1**: "실시간 갱신이 안 되는 것은 아쉽다"는 의견에 **열 때 대조**를 F1 로 당겼다. 폴더 2만 개 mtime 확인이 4스레드 11ms 라,
  데몬 없이도 런처를 여는 순간 바뀐 폴더를 찾아 그 검색에 반영할 수 있다. 데몬 감시(F3)는 "런처를 열지 않아도" 공개되게 하는 몫으로 남는다.
