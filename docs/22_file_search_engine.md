# 22. 파일 검색 엔진 — 수십만 개를 세 OS에서 똑같이 빠르게

> 상태: **설계 v3.1** (2026-10-26, 브랜치 `bullpae/file-search`) — 초안을 Claude Fable 5.1·Opus 5.5 가 검토해 v2, GPT Astra 검토를 더해 v3(§7).
> 계기: Windows 10 사용자 보고 — `:scope` 로 `E:\MyOffice` (파일 약 40만, 폴더 약 8,200)를 넣었더니
> `2022년` 이후 폴더가 검색되지 않음. 직접 원인은 커밋 08ed07c 에서 고쳤다(§2.1). 이 문서는 근본 구조를 다룬다.
> 관련: [18_search_scope_ux.md](18_search_scope_ux.md)(`:scope`), [15_content_search_plan.md](15_content_search_plan.md)(본문 검색, FTS5 — 이 문서 범위 밖)

## 1. 목표

| | 목표 |
|---|---|
| 규모 | 검색 범위 안 파일 **100만 개**까지 할당량 없이 색인 (안전 상한 `max_files` 만 남김) |
| 런처 시작 | 색인 크기와 무관 — 런처는 파일 색인을 읽지 않는다 |
| 키 입력 → 결과 | 데몬 검색 **p95 5ms** (40만, **4코어 Windows 기준**), IPC 포함 10ms |
| 정확성 | 결과가 덜 나오거나 이전 질의 결과가 남는 일이 없다 (§2.2-2) |
| 신선도 | NTFS·APFS·ext4 로컬 디스크는 **수 초**, 그 밖의 볼륨은 주기 재스캔 주기 안 |
| 이식성 | 세 OS 같은 코드 경로. Everything·Spotlight 는 선택 가속 |
| 자원 | 40만 기준 **FileTable 40MB 안팎**(시작 예산, 실측으로 조정). 데몬 전체 RSS 는 따로 잰다. 키 훅을 굶기지 않는다(2026-08-08 수칙) |

**하지 않는 것**: 본문 검색(docs/15), 범위 밖 디스크 전체 검색(Everything 영역), MFT 직접 읽기(관리자 권한).

## 2. 지금 구조와 문제

### 2.1 구조

```
데몬: 6시간마다 Index::build → index.bin + index.json, 자기 SearchEngine(Mutex) 갱신
런처(단축키마다 새 프로세스): quick-index.bin → 표시 → index.bin → SearchEngine(nucleo) 구성
검색: update 안에서 동기 호출 (search_routing.rs:296) → 모드 판정 → 결과 → frecency 가중(:319)
IPC: 127.0.0.1 TCP + 토큰 (ipc.rs:5-11), 연결 하나에 요청 하나 (server.rs:681-715), 연결마다 스레드
```

- 파일 수집: `collect_priority_files`(walkdir 단일 스레드) + 일반 프로바이더가 남은 할당량을 채움. 상한 `launcher.max_results` 기본 5000.
- 08ed07c: 폴더는 할당량 밖(5만까지), 파일 몫은 검색 폴더별로 나누고 얕은·최근 우선. **파일 상한은 남아 있다.**
- 데몬 IPC `Request::Search` 는 있지만 데스크톱 런처는 쓰지 않는다.

### 2.2 측정과 문제 (M 시리즈 18코어, release, 합성 항목)

| 항목 수 | index.bin | 로드 | `SearchEngine::with_items` | 한 글자 | "보고서 최종"(contains) |
|---|---|---|---|---|---|
| 5천 | 1MB | 1ms | 13ms | 1ms | 3ms |
| 5만 | 10MB | 9ms | 61ms | 2ms | 24ms |
| 40만 | 79MB | 79ms | 494ms | 11ms | 188ms |

1. **런처 시작 비용이 색인 크기에 비례** — 40만이면 창마다 +0.5초.
2. **결과 누락** — `search_fuzzy` 가 `nucleo.tick(10)` 을 한 번만 부른다(search.rs:297). 40만에서 `2` → 0건, 이어 `zzzz` → 이전 결과 50건.
3. **contains 가 느리다** — 항목마다 경로 조각 `HashSet` 을 새로 만든다(search.rs:402).
4. **점수가 품질이 아니다** — 퍼지 점수는 순위 `(count−i)*10`(search.rs:308)이라 kind 가중(폴더 80·앱 70, types.rs:359)이 매칭 품질을 압도한다.
5. **항목이 무겁다** — 경로를 `path`·`keywords` 에 두 번, 아이콘 문자열까지(≈130~200B/항목).

### 2.3 다른 도구들

| 도구 | 방식 |
|---|---|
| Everything | MFT 적재, 서비스가 **이름 배열 + 부모 참조**를 상주, USN 저널 갱신, IPC 질의 |
| Flow Launcher·PowerToys Run·Listary | 자체 색인 없이 Everything/Windows Search 위임 |
| Alfred·Raycast | 파일은 Spotlight 위임 |
| plocate | 트라이그램 역색인 — 수천만 규모용 |
| fzf | 색인 없이 선형 스캔 — 수백만도 충분 |

공통점: **큰 파일 목록은 상주 프로세스가 들고, 런처는 묻는다.** 100만 이하에서는 역색인보다 캐시 친화적 선형 스캔이 단순하고 빠르다.

## 3. 설계

### 3.1 한눈에

```
                ┌──────────────────────────── kmd-daemon ────────────────────────────┐
 :scope 폴더 ──▶ │ Scanner ─▶ FileTable(구조 배열, ArcSwap 스냅숏) ◀─ Updater(F3)       │
                │                 │                                                  │
                │      Query: 모드별 거르기 → 싼 점수로 상위 5천 → Matcher → rank::combine │
                │                 │                    ▲ frecency(history DB)        │
                └─────────────────┼────────────────────┴──────────────────────────────┘
                                  │ IPC FileSearch (비동기 Task, 세대 번호, 타임아웃 100ms)
 런처 ── quick-index(앱·명령·최근) 즉시 ── 파일 결과 합치기(같은 rank::combine) ── 데몬 없으면 스냅숏 읽기 전용 폴백
```

### 3.2 FileTable — 구조 배열

```rust
struct FileTable {
    raw: Vec<u8>,         // 원본 이름 바이트 (Unix: OsStr 바이트, Windows: WTF-8) — 경로 복원은 이것으로만
    raw_off: Vec<u32>,
    folded: Vec<u8>,      // 검색용: NFC + 소문자. 이름 사이에 구분 바이트 0x00
    folded_off: Vec<u32>, // 접으면 길이가 변한다(İ, K 기호, NFD→NFC) → 오프셋 따로
    parent: Vec<u32>,     // 부모 폴더 행 (루트 u32::MAX)
    bag: Vec<u64>,        // 문자 가방: ASCII 영숫자 36비트 + 한글 초성 19비트 + 기타 비트
    meta: Vec<Meta>,      // kind 2bit·깊이·확장자 id·숨김·삭제·클라우드 자리표시자
    mtime: Vec<i64>,      // 전체 해상도 — 순위 가중과 갱신 대조 모두
    root_id: Vec<u16>,    // 행이 속한 검색 폴더 — 갱신으로 행이 뒤에 붙으므로 "루트별 행 범위"는 쓰지 않는다
    roots: Vec<RootInfo>, // 검색 폴더별 볼륨 종류·상태(온라인·오프라인·감시 불가)·스캔 세대
    dir_ids: HashMap<(u64, u64), u32>, // 폴더만: (볼륨 id, FileId/inode) → 행. 이동 판별용 (F3)
}
```

- **원본과 검색용을 분리**: 이름을 NFC로 바꿔 저장하면 ext4·SMB 에서 맥발 NFD 이름을 열 수 없고, Windows 이름의 짝 없는 서로게이트는 UTF-8로 못 담는다.
- **전체 경로는 저장하지 않는다.** 결과 상위 N개만 `parent` 를 따라 복원.
- 메모리(40만): raw·folded 각 ~14MB + 오프셋·parent·bag·meta·mtime ~10MB ≈ **38MB**.
- **행 수명**: 행 번호(u32)가 항목 id 이자 `parent` 참조다. 지운 행을 **재사용하지 않는다** — 재사용하면 정리되지 않은
  자식의 `parent` 가 엉뚱한 폴더를 가리켜 잘못된 경로가 나온다(`2022년/보고서` → `2026년/보고서`).
  삭제는 tombstone 플래그, 새 행은 뒤에 붙인다. 삭제 비율이 일정 이상이면 압축(compaction)으로 행 번호를 다시 매기고
  `parent`·`dir_ids` 를 재구성한 뒤 세대를 올린다. 재사용이 꼭 필요해지면 `(slot, generation)` id 로.
- 파일 id 는 폴더에만 둔다(8천 개) — 이동 판별이 필요한 건 대부분 폴더이고, 파일 40만 개에 u64 를 두면 3MB 다.
- **읽기·쓰기 분리**: 읽기는 세대가 고정된 불변 스냅숏(`ArcSwap`)이라 갱신 중에도 검색이 막히지 않는다
  (지금 `Mutex<SearchEngine>`, server.rs:858 와 다르게). 단 변경마다 테이블 전체(수십 MB)를 복제하지 않는다 —
  **불변 기본 테이블 + 작은 변경분(overlay: 추가 행·tombstone 집합)** 을 함께 읽고, 변경분이 커지면 백그라운드에서
  합쳐 새 기본 테이블로 교체한다. 변경 묶음은 debounce 단위로 한 번에 반영.
- 기존 `search_depth`(기본 4)는 그대로 검색 폴더별 깊이 상한으로 쓴다.

### 3.3 질의

질의는 `SearchMode::detect` 를 그대로 쓰고, 토큰을 공백으로 나눈다.

**1. 거르기 (모드별)**

| 토큰 | 방법 |
|---|---|
| 비ASCII(한글 등) | `folded` 블롭 **전체**에 `memchr::memmem::Finder` 한 번 → 히트 오프셋을 `folded_off.partition_point` 로 행으로. 16MB ≈ 1.5ms 단일 스레드 |
| ASCII, 3글자 이상 | `bag` AND 로 먼저 거름(대부분 탈락) → 남은 것만 subsequence |
| ASCII, 1~2글자 | **별도 경로**: 접두·단어 시작 일치만 후보로 (subsequence 로는 `2` 가 27만 개 통과) |
| glob·확장자 | 확장자 id 비교 → 패턴 |
| regex | 후보 상한 있는 선형 스캔 |

- 혼합 질의(`2026 보고`)에서 비ASCII 토큰을 바이트 subsequence 로 돌리지 않는다 — UTF-8 연속 바이트가 다른 음절과 교차 매칭된다.
- **여러 토큰·경로 질의**: 토큰마다 **폴더 8,200개만** 먼저 매칭해 `folder_mask[f]`(토큰 비트)를 만들고
  `anc_mask[f] = folder_mask[f] | anc_mask[parent[f]]` 로 한 번 전파. 파일은 `(own_mask | anc_mask[parent]) == ALL` 한 번 확인. O(폴더×토큰 + 파일) ≈ 1ms.
- 실행은 **상주 스레드 풀**(코어/2, 최대 4, 낮은 우선순위). 질의마다 스레드를 띄우지 않는다.

**2. 점수**

1. 후보가 5천을 넘으면 **거르기를 통과한 모든 후보**에 싼 점수(정확·접두·단어 시작·이름 길이·frecency 유무)를 매겨 상위 5천을 `select_nth_unstable`.
   먼저 발견된 순서로 자르지 않는다 — 가장 정확한 `보고서_최종.docx` 가 1만 5천 번째에 있어도 남아야 한다.
   싼 점수와 Matcher 점수가 어긋나 1위를 놓치는지는 골든 셋으로 확인하고, 놓치면 K 를 키우거나 싼 점수를 고친다.
2. 그 안에서만 nucleo `Matcher` 로 품질 점수(`Nucleo` 워커·tick 미사용 → §2.2-2 구조적 해소).
   **거르기는 Matcher 의 상위 집합이어야 한다** — 후보를 많이 남기는 건 괜찮지만, Matcher 가 맞다고 할 항목을 빼면 안 된다(§5 테스트).
3. `rank::combine`(§3.4)으로 최종 점수, 상위 `limit`(상한 200) 반환.

**3. 이어 치기 좁히기** (F1 이후 측정 보고 결정): fuzzy·contains 에서만, 새 질의가 이전 질의를 확장하고 세대·모드가 같을 때만. glob·regex 는 단조가 아니라 쓰지 않는다.

### 3.4 순위 — 한 곳에서

지금은 퍼지 순위 점수에 kind 가중과 frecency 를 더해 품질이 묻힌다(§2.2-4). `kmd_core::rank::combine` 하나로 모은다.

```
final = match   (0..100 nucleo 정규화; 정확 +40, 접두 +25, 단어 시작 +15)
      + where   (이름에서 매칭 ×1.0, 조상 폴더에서만 ×0.6)
      + kind    (앱 +20, 폴더 +15, 파일 0)        ← 정확 일치보다 작게
      + frecency(최대 40)
      + recency (mtime 1일 +15, 1주 +10, 1달 +5)
      − depth   (검색 루트 아래 단계당 2, 최대 10)
동점: 이름 짧은 순 → 최근 수정 순
```

- **frecency 는 데몬이 읽는다**: 데몬이 상위 K만 돌려주면 자주 여는 파일이 K 밖에서 영영 부스트를 못 받는다. 데몬이 history DB 를 읽어 거르기 단계의 싼 점수부터 반영하고, 실행 기록이 바뀌면 다시 읽는다.
- 런처는 quick-index 결과와 파일 결과를 **같은 `rank::combine`** 으로 합친다(점수 척도 공유). `boost_results_with_map` 은 이것으로 대체.
- 바꾸기 전에 실사용 이력으로 **골든 셋**("질의 → 기대 1위")을 만들어 회귀를 본다. 앱·PATH 순서도 바뀌므로 필수.

### 3.5 스캐너 — 첫 스캔

- 병렬 걷기(`jwalk` 또는 `ignore::WalkParallel`), 무시 규칙은 기존 함수(`is_ignored_dir`·확장자·숨김·macOS 패키지) 그대로.
- 스레드 상한(코어/2), 낮은 우선순위(macOS QoS utility, Windows background mode, Linux nice). 스캔 중에도 넣은 행은 검색된다("색인 중 n개").
- **OneDrive 등 클라우드 자리표시자**(RECALL_ON_OPEN·RECALL_ON_DATA_ACCESS 속성): 나열만 하고 열지 않는다(아이콘·본문 색인 금지 — 하이드레이션 유발). 아직 내려받지 않은 폴더는 내려가지 않는 옵션.
- 네트워크·외장 루트는 시간 예산과 "느린 루트" 표시.

### 3.6 갱신 (F3)

볼륨 종류를 먼저 판별한다(`GetVolumeInformationW`·`statfs`).

| 볼륨 | 방법 |
|---|---|
| NTFS·ReFS·APFS·HFS+·ext4·btrfs (로컬) | `notify` 변경 알림 + 폴더 mtime 대조 안전망 |
| FAT32·exFAT | 폴더 mtime 이 하위 변경에 갱신되지 않음 → 알림 + **주기 재나열**(시간 예산) |
| SMB·NFS | 디렉터리 캐시(SMB ~10초, NFS ~30초) → 주기 재나열, 알림은 보조 |
| 외장 HDD | 콜드 stat 이 디스크를 깨움 → 알림 오버플로·절전 복귀 때만 대조 |

- **알림**: 경로를 모아(debounce) **그 폴더 하나만 다시 나열**해 차이를 반영. 새로 생긴 하위 폴더는 재귀로 걷는다.
  - 이동·이름 변경은 `file_id` 로 판별해 **`parent`·이름 한 칸만 교체**(서브트리 재스캔 없음 — 부모 참조 모델의 장점). 삭제는 서브트리 플래그.
  - 대소문자만 바꾼 이름 변경은 `raw` 로 비교(접힌 키로 비교하면 놓친다). 대소문자 구분 FS 에서 접힌 키로 중복 제거하지 않는다.
  - 버퍼 넘침(Windows `ERROR_NOTIFY_ENUM_DIR`, notify `Rescan` 플래그)·FSEvents `MustScanSubDirs`·절전 복귀·볼륨 재연결(볼륨 시리얼 확인) → 그 하위 트리 또는 루트 대조.
  - inotify `max_user_watches` 한도(구 커널 8,192) 초과 → 주기 재나열로 동작하고 상태에 표시.
  - Windows 재귀 감시는 루트 핸들을 열어 두어 외장 디스크 꺼내기를 막는다 → 볼륨 제거 알림에 감시 해제.
  - 본문 색인 감시(`spawn_content_watcher`, server.rs:389)와 **감시자를 공유**.
- **폴더 mtime 대조**: mtime(전체 해상도)과 항목 수를 함께 비교해 바뀐 폴더만 재나열. 파일 40만 개를 stat 하지 않는다.
  유일한 복구 수단이 아니다 — 타임스탬프가 복원되거나(백업 복원) 원격 FS 가 다르게 굴면 놓친다 → 유휴 시 **분할 전체 재스캔**(하루 한 바퀴)이 최종 안전망.

**이벤트는 "변경 목록"이 아니라 "여기는 더 이상 믿을 수 없다"는 신호로 다룬다.** 모든 경로가 한 큐로 모인다.

```
OS 감시(notify) ─┐
mtime 대조 ──────┼─▶ 정규화 ─▶ Dirty 큐 ─▶ 백그라운드 대조기 ─▶ 변경분 ─▶ 새 읽기 세대
절전 복귀·재연결 ─┤              ├ DirtyEntry   : 그 폴더 한 단계 재나열
분할 재스캔 ─────┘              ├ DirtySubtree : 폴더와 하위 전부 (새 폴더, MustScanSubDirs, 대량 이동)
                                └ DirtyRoot    : 루트 전체 검증 (버퍼 넘침, 감시 재설정)
```

- 같은 폴더 이벤트는 합치고, 하위 Dirty 는 상위 Subtree 에 흡수, 큐가 넘치면 Root 로 격상.
- **데몬 시작 순서**: 스냅숏 로드 → **감시 먼저 등록** → 루트별 대조(꺼져 있던 동안의 변경). 대조 중 들어온 이벤트는 큐에 쌓였다가 이어서 처리.
- **외장 디스크 분리**: 색인을 지우지 않고 루트를 오프라인으로 표시(결과에 흐리게 + "연결 안 됨"), 재연결 시 볼륨 시리얼이 같으면 대조, 다르면 재스캔.
- **신선도는 두 등급으로 약속한다**: 로컬·감시 정상 = 수 초. 감시 불가·원격·오프라인 = 폴링 주기만큼 지연, `kmd index --stats` 에 루트별 상태로 보인다.

### 3.7 런처 ↔ 데몬 (F2)

- 새 IPC `FileSearch { query, limit, gen }` → `FileResults { gen, total, items: [{name, path, kind, features…, score}] }`. 기존 `Search` 호환 유지, `limit` 상한 200.
- **런처는 비동기로 받는다**: 지금처럼 update 안에서 동기 호출하면 데몬이 멈출 때 UI 가 최대 5초(ipc.rs:378) 언다.
  `handle_clip_query`(search_routing.rs:159) 선례처럼 Task, 타임아웃 100ms.
- **요청 번호와 색인 세대는 다른 것이다**: 요청에 `request_id`(런처 안에서 증가)와 응답에 `index_generation` 을 모두 둔다.
  `보고`(15ms)보다 `보고서`(3ms) 응답이 먼저 오면, 늦게 온 `보고` 응답은 `request_id` 가 현재와 달라 버린다. 데몬은 같은 연결의 낡은 요청이 큐에 있으면 건너뛴다.
- **"결과 없음" 판정은 파일 결과가 온 뒤로 미룬다** — 그 전에 한글 완화 검색·웹 제안(search_routing.rs:333, 347)이 먼저 뜨면 안 된다. quick 결과는 **즉시** 그리고, 파일 결과는 오는 대로 합친다 — 다음 프레임 전에 왔으면 같은 프레임에 합친다. UI 스레드에서 기다리지 않는다("20ms 모아 그리기"는 모든 검색에 지연을 더하므로 쓰지 않는다).
- 연결: 처음엔 **지금 프로토콜 그대로**(연결당 요청 하나, 루프백 연결 ~0.5ms). Windows 에서 키 입력당 2ms 넘으면 연결 유지 + 길이 접두 프레임으로 바꾼다(서버 루프·연결 슬롯 변경 필요).
- **데몬·런처 버전 불일치**: 릴리스 채널이 여럿(brew·winget·포터블)이라 `FileSearch` 를 모르는 데몬이면 폴백.
- **폴백**: 데몬이 없으면 §3.8 스냅숏을 **읽기 전용 mmap** 으로 열어 같은 질의 코드로 검색(옛 `index.bin` + 494ms 로 돌아가지 않는다). 스냅숏도 없으면 지금 경로.

### 3.8 스냅숏 (F1 에서 형식 확정)

- FileTable 열을 그대로 파일 하나에(헤더·버전·열 길이·체크섬). **mmap 으로 바로 읽을 수 있는 정렬된 평탄 배열** — 메모리 레이아웃 자체라 F1 에서 정한다.
- 데몬 재시작: 읽어서 즉시 검색, 이어서 §3.6 대조로 따라잡기.
- 쓰기: **세대별 파일명**(`files.<gen>.snap`) + 포인터 파일. Windows 는 매핑 중인 파일을 rename 으로 덮을 수 없고, Unix 는 덮어쓰기·truncate 가 SIGBUS 를 낸다 → 새 세대를 쓰고 포인터만 바꾸고, 옛 세대는 지연 삭제.
- 위치는 표준 데이터 폴더(포터블이면 `kmd-data/`), Unix 0600. 파일 이름 목록 자체가 민감하다 — 질의는 로그에 남기지 않는다.

### 3.9 한글

- `folded` 는 NFC 소문자(macOS NFD 이름은 넣을 때 NFC). 질의도 NFC(기존 규칙).
- (F4) **초성**: 질의에 호환 자모가 있을 때만 즉석 분해로 시작(40만×15자 ≈ 6ms 단일), 느리면 열로. 마지막 미완성 음절(`보고ㅅ` → 보고서)도 초성으로.
- (F4) **한영 오타 변환**: `qhrhtj` → 보고서. 영문 자판 상태로 친 질의를 두벌식으로 바꿔 한 번 더 찾는다 — Windows 에서 체감이 크다.

### 3.10 OS 인덱서 가속 (F4, 선택)

- Windows + Everything 실행 중: 범위 밖 질의나 사용자 선택 시 Everything IPC(SDK)로 위임. `es.exe` 를 키마다 띄우지 않는다.
- Spotlight `mdfind` 는 키마다 프로세스라 기본 경로로 쓰지 않는다.
- 설정 `launcher.file_backend = "auto" | "builtin" | "everything"`.

### 3.11 보안

**신뢰 경계는 같은 사용자 계정이다.** 같은 계정으로 도는 악성 프로그램은 IPC 를 막아도 디스크를 직접 읽을 수 있으므로,
IPC 접근 통제만으로 그것을 막는다고 주장하지 않는다. 목표는 (1) 다른 계정·다른 PC·웹 페이지가 닿지 못하게,
(2) 데몬이 검색 이상의 능력을 IPC 로 내주지 않게, (3) 색인 파일이 새는 경로를 만들지 않게.

**지금 IPC 가 이미 갖춘 것**: `127.0.0.1` 에만 묶고 무작위 포트(server.rs:598), 32바이트 토큰·상수 시간 비교(server.rs:698),
토큰 파일은 사용자 데이터 폴더(Unix 0600, 포터블 폴더 아님, ipc.rs:247), 요청 64KB·동시 연결 64개 상한(server.rs:690·190),
regex 컴파일 크기 상한(search.rs:341). 웹 페이지는 토큰을 몰라 첫 줄에서 끊긴다(DNS 리바인딩 포함).

**점검 중 발견 — 지금 IPC 의 능력 범위가 넓다** (파일 검색과 별개로 F0 와 함께 고친다):

- 같은 토큰 하나로 검색뿐 아니라 키 주입(`InjectPaste`·`PasteEnter`·`EnterOnly`), 클립보드 기록 읽기(`ClipHistory`),
  현재 위치(`Location`), URL 열기(`LlmAutopilot`)까지 된다. 같은 계정 경계 안이라 권한 상승은 아니지만, 토큰이 새면 피해 범위가 크다.
- **`LlmAutopilot` 의 `url` 을 데몬이 검사하지 않는다** — `open_url` 이 http(s) 가 아니면 Windows 에서 `explorer.exe <경로>` 로 연다(action.rs:95-111).
  즉 IPC 로 임의 파일을 실행할 수 있다. → 데몬 쪽에서 `https://` 만 받고 나머지는 거절(SEC-03).

**요구사항**

| ID | 요구사항 | 단계 |
|---|---|---|
| SEC-01 | 사용자별 IPC 접근 통제·원격 차단. 지금 TCP+토큰 유지, 전송 교체 시 Windows 네임드 파이프는 **현재 사용자 SID 만 허용하는 ACL + `PIPE_REJECT_REMOTE_CLIENTS`**, Unix 소켓은 사용자 전용 디렉터리(0700) + 소켓 0600 + 상대 자격 확인(Linux `SO_PEERCRED`, macOS `getpeereid`)으로 uid 일치 확인 | F2 |
| SEC-02 | 데몬은 **일반 사용자 권한**으로만(지금도 LaunchAgent·사용자 자동 시작). 관리자로 실행되면 경고하고 파일 색인을 하지 않는다 — 관리자 데몬이 일반 사용자에게 다른 프로필의 파일 이름을 내주면 안 된다 | F1 |
| SEC-03 | **검색 전용 응답, 입력 상한**: `FileSearch` 는 이름·경로·종류·점수·mtime 만 반환(본문·임의 경로 읽기·실행 없음). 질의 4KB, `limit` 200, regex 크기·실행 후보 상한, 처리 시간 상한(넘으면 부분 결과 + 표시). 기존 `LlmAutopilot` URL 은 https 만 | F0(URL)·F2 |
| SEC-04 | 색인 파일 보호: 사용자 전용 디렉터리(`LocalAppData`·`~/Library/Application Support`·`$XDG_DATA_HOME`, Unix 0700/0600). 새 세대는 **같은 디렉터리에 `create_new` 로 만들고**(심볼릭 링크를 따라가지 않음, Unix `O_NOFOLLOW`), 포인터 파일만 원자적으로 교체. 디렉터리 소유자가 현재 사용자가 아니면 쓰지 않는다 | F1·F3 |
| SEC-05 | IPC 가 안 되는 환경에서 **내장 모드**(§3.12) | F2 |
| SEC-06 | 읽지 못하는 폴더는 건너뛰고 "n개" 만 기록 — 경로를 로그에 남기지 않는다. 질의 문자열도 로그·오류 메시지에 남기지 않는다(길이만) | F1 |
| SEC-07 | 진단: `kmd daemon status` 에 IPC 왕복 시간과 실패 분류(연결 거부·시간 초과·토큰 불일치·정책으로 꺼짐) | F2 |
| SEC-08 | 테스트: 잘못된 토큰·긴 질의·악성 regex·잘린 프레임·동시 연결 폭주, 손상된·버전 다른·심볼릭 링크로 바꿔치기된 스냅숏 | F2·F3 |

후속(선택): 토큰을 능력별로 나누기 — 런처에는 검색·클립보드 토큰, 키 주입은 데스크톱 런처 실행 파일만. 같은 계정 경계라 완전한 방어는 아니므로 우선순위는 낮다.

### 3.12 IPC 가 막혀 있을 때 — 내장 모드

**막힐 수 있는 경우**

- Windows 방화벽은 루프백을 기본으로 거르지 않지만, 회사 보안 제품(EDR·EPP·DLP, 일부 백신의 WFP 필터, 제로 트러스트 VPN)이 로컬 TCP 를 검사·차단할 수 있다.
  네임드 파이프·유닉스 소켓은 TCP 포트를 열지 않아 방화벽 규칙 대상이 아니지만, EDR 이 프로세스 간 통신 자체를 막으면 이것도 막힌다.
- 데몬 실행 자체가 막히거나(애플리케이션 제어), 아직 안 떴거나, 죽은 경우.
- 키마다 새 TCP 연결 → Windows TIME_WAIT 소켓 누적(초당 10회 → 4분에 2,400개).

이미 클립보드 기록(`:c`)·`kmd daemon status` 가 같은 IPC 를 쓰므로, 그 PC 에서 이들이 되면 파일 검색 IPC 도 된다.

**구조 — 같은 검색 코어, 백엔드 둘**

```
런처 ── FileSearchClient ──┬─ 데몬 모드: IPC → 데몬의 FileTable (기본)
                          └─ 내장 모드: 스냅숏 mmap → 런처 프로세스 안에서 같은 Query 코드
```

검색 정확도·순위는 공통 코어라 같다. 차이는 신선도와 런처 메모리(스냅숏 페이지가 런처에 올라옴).

**내장 모드의 신선도** — 런처는 단축키마다 새 프로세스라 감시를 상주시킬 수 없다:

1. 데몬이 살아 있고 IPC 만 막힌 경우: 데몬이 스냅숏을 계속 쓰므로 신선도는 스냅숏 주기(변경 묶음 단위)만큼.
2. 데몬 자체가 없는 경우: 런처가 창을 띄운 **뒤** 백그라운드 스레드에서 스냅숏이 오래됐으면(기본 10분) 폴더 mtime 대조로 변경분을 만들어
   다음 세대를 쓴다(볼륨별 규칙 §3.6 그대로, 시간 예산·낮은 우선순위). 런처가 닫히면 중단 — 다음 런처가 이어서.
3. 둘 다 안 되면(쓰기도 막힘) 읽기만 하고 상태 줄에 "색인 n분 전".

**자동 전환 규칙**

- `auto`: 첫 요청이 연결 실패·100ms 초과면 그 런처 동안 내장 모드. 키마다 재시도하지 않는다.
- **정책으로 꺼진 것과 단순 실패를 구분한다**: 설정 `ipc_enabled = false`(관리자 배포 설정 포함)면 IPC 를 아예 시도하지 않는다.
  막혔을 때 다른 전송 방식으로 몰래 바꿔 재시도하지 않는다 — 보안 정책을 우회하는 동작으로 보일 수 있다. TCP→파이프 전환은 설정·버전으로만.
- 공유 메모리는 쓰지 않는다 — 접근 권한·동기화 문제를 새로 떠안고, 막는 정책도 같다. IPC 지연이 병목이라는 측정이 나오면 그때 검토.

**설정**

```toml
[launcher.file_search]
backend = "auto"        # auto | daemon | embedded
ipc_enabled = true      # false = IPC 시도 안 함 (회사 정책 등)

[launcher.file_search.limits]
max_query_bytes = 4096
max_results = 200
max_files = 1000000
```

원격 접속 옵션(`allow_remote`)은 두지 않는다 — 원격 검색은 지원하지 않는다.

엄격한 보안 PC 에서는 IPC 뿐 아니라 백그라운드 데몬, 파일 감시, 특정 폴더 접근도 각각 막힐 수 있다. 내장 모드는 "IPC 없이도 검색"을 보장할 뿐,
그런 환경 전부에서 동작한다고 보장하지 않는다. 막힌 기능은 상태로 보여 준다.

### 3.13 호환성 정책

| 항목 | 정책 |
|---|---|
| 심볼릭 링크·정션 | 따라가지 않는다(지금 `follow_links(false)` 와 같음). 순환·중복 방지 |
| 중첩 scope | 같은 경로를 두 번 색인하지 않는다 — 추가 단계에서 이미 막고(`covering_root`), 색인에서도 루트 간 중복 제거 |
| 대소문자 | 검색은 공통 규칙(접은 이름). 같은 파일인지는 FS 의미론(원본 이름·id)으로 판단, `lowercase(path)` 로 판단하지 않는다 |
| 권한 없는 폴더 | 건너뛰고 루트 상태에 "읽지 못한 폴더 n개" 기록 |
| 외장 디스크 | 분리 시 오프라인 표시, 색인 보존(§3.6) |
| 네트워크 경로 | UNC·SMB·NFS 는 폴링 등급(§3.6) |
| macOS 앱 번들 | 지금처럼 `.app` 하나, 안으로 내려가지 않음(docs/18 §9) |
| `max_files` 초과 | 얕은·최근 우선으로 담고(08ed07c 규칙) **"색인 불완전 — n개 빠짐"** 을 `:scope`·stats 에 표시. 조용히 빼지 않는다 |
| IPC 접근 | §3.11·§3.12 |

## 4. 단계

| 단계 | 내용 | 완료 조건 |
|---|---|---|
| **F0** (이번 PR `bullpae/scope-quota`) | 08ed07c + `search_fuzzy` 가 끝났는지(`status.running`) 확인: tick 반복(상한 50ms), 그래도 안 끝났으면 **다음 프레임에 다시 물어 갱신** + `filter_contains` HashSet 제거 + `LlmAutopilot` URL 은 https 만(SEC-03) | 40만 `2`→`zzzz` 에서 이전 결과가 남지 않음(50ms 상한은 응답성 장치일 뿐 완료 조건이 아니다), "보고서 최종" 10배 이상 |
| **F1** | FileTable + 모드별 거르기(memmem·bag·1~2글자 경로·폴더 마스크) + 싼 점수→Matcher + 상주 풀 + **스냅숏 형식**. 데몬 안에서만 | 4코어 제한·한글 이름·깊이 4~7 합성 트리 벤치 p95 5ms, 현 엔진과 차등 테스트 |
| **F2** | IPC `FileSearch`(request_id) + 런처 비동기 합치기 + `rank::combine` + 골든 셋 + 스냅숏 폴백. 파일 할당량 제거는 **설정 뒤에 숨긴 채**로 | Windows 실기에서 키 입력당 IPC 측정, 골든 셋 통과 |
| **F3** | notify 공유 + Dirty 큐·대조기 + 볼륨별 갱신 전략 + 폴더 id 이동 처리 + 스냅숏 세대 쓰기. 검증 후 **할당량 제거를 기본으로 켠다** — 첫 스캔은 되는데 변경이 반영되지 않으면 더 나쁜 검색이다 | NTFS 실측(폴더 mtime, 대소문자 변경, 260자 경로, 10만 개 폭주) |
| **F4** | 초성·한영 변환·Everything 위임·`kmd index --stats` 루트별 수·느린 루트 | |

**별도 축**: 런처 상주(숨긴 창 + 단일 인스턴스)는 체감 효과가 클 수 있지만 파일 검색과 직교. Windows 에서 단축키→창 표시 시간을 먼저 재고 따로 결정.

## 5. 테스트

- **참조 구현과 차등(proptest)**: 현 엔진은 tick 문제가 있어 정답으로 삼지 않는다. 작은 데이터용으로 느리지만 확실한 참조 구현(전 항목에 Matcher·contains 직접 적용)을 두고 비교한다.
  한글·NFD·대소문자 섞인 이름을 무작위 생성. contains·glob·regex 는 결과 **집합**이 같아야 하고, 퍼지는 FileTable 후보 ⊇ Matcher 매칭.
- **상태 전이**: 폴더 통째 이동, 대량 삭제 후 추가(tombstone·압축 뒤 `parent` 무결성), 감시 버퍼 넘침 → 완전 복구, 데몬 강제 종료 → 스냅숏 복구, 스캔 중 검색(부분 결과 표시), 외장 디스크 분리·재연결, 중첩 scope 중복 없음, 권한 없는 폴더, 장시간 수정 반복 후 메모리.
- **경로 복원 퍼징**: 원본 이름 → 경로 복원이 원래 경로와 바이트 단위로 같아야 한다(서로게이트·NFD 포함).
- **벤치**: CI 는 시간 대신 명령어 수(iai-callgrind)로 회귀만. 시간 벤치는 로컬·Windows 실기에서 **1·2·4·8 스레드** 각각, 질의 종류(1~2글자·일반·경로·한글)별 p95 를 따로 — 하나의 숫자로 묶지 않는다. 40만과 100만은 목표를 따로 둔다.
- **Windows 실측**(F3 전): NTFS 폴더 mtime 갱신, 대소문자만 바꾼 이름 변경, 긴 경로, 이벤트 폭주로 버퍼 넘침.

## 6. 위험

1. **1~2글자 후보 폭발**(27만) — §3.3 별도 경로와 후보 상한이 없으면 5ms 목표가 무너진다.
2. **사용자 PC 코어 수** — 4코어면 거르기 3~4ms. 상주 풀 상한·우선순위로 키 훅과 경쟁하지 않게.
3. **볼륨별 갱신 차이** — 판별 없이 mtime 대조만 믿으면 FAT·SMB 에서 "지웠는데 남는" 결과.
4. **IPC 의미 변경과 버전 불일치** — 비동기 전환, 연결 유지(필요 시), 채널 간 버전 차.
5. **순위 전면 교체** — 골든 셋 없이는 회귀를 못 본다.

## 7. 검토 반영 (2026-10-26)

초안을 Claude Fable 5.1·Opus 5.5 가 따로 읽기 전용으로 검토했다. 둘 다 지적해 반영한 것:

- IPC 는 소켓/파이프가 아니라 **TCP + 토큰, 연결당 요청 하나** — 사실 오류 수정(§2.1, §3.7).
- **1~2글자 후보 폭발**과 "상위 K 를 고르려면 전부 점수화" 문제 → 싼 점수·후보 상한·별도 경로(§3.3).
- **`name_off` 공용 불가**(접으면 길이 변함), 원본 이름 보존(§3.2).
- **폴더 mtime 대조는 FAT·SMB·NFS 에서 무효/지연** → 볼륨별 전략(§3.6).
- **부모 참조 모델로 이동은 한 칸 교체**, 루트 재스캔은 과잉(§3.6).
- notify 함정(Rescan, inotify 한도, Windows 루트 핸들), 질의마다 스레드 spawn 금지(§3.3, §3.6).
- frecency 위치 문제(§3.4).

한쪽만 지적해 반영한 것:

- Opus: 런처 **동기 검색**이 데몬 지연에 UI 를 얼리고 "결과 없음" 폴백이 먼저 뜬다(§3.7), mtime 분 단위 부족, OneDrive 자리표시자, 스냅숏 mmap 폴백, 스냅숏 위치·권한, 차등·퍼징 테스트.
- Fable: contains 블롭 memmem·**문자 가방**, **폴더 마스크 경로 질의**, 현 점수가 순위라 kind 가중이 품질을 압도(§2.2-4), `filter_contains` HashSet(F0 에 포함), 한영 오타 변환.

갈린 것과 결정:

- **frecency** — Opus "데몬이 history DB 를 읽는다" / Fable "데몬은 특징만, 런처가 합산". → 데몬이 읽어 후보 선정부터 반영하고, 합산 함수는 `rank::combine` 하나를 양쪽이 공유(§3.4).
- **연결 유지** — Opus "일단 지금 프로토콜, 0.5ms 허용" / Fable "연결 유지 + 프레임". → 지금 프로토콜로 시작해 Windows 실측 후 결정(§3.7).
- **이어 치기 좁히기·스냅숏 시점** — Opus 는 첫 마일스톤에서 제외, Fable 은 스냅숏을 F1 로. → 스냅숏 **형식**은 F1(메모리 레이아웃이자 폴백 경로), 쓰기 세대 관리는 F3. 좁히기는 F1 측정 후.
- **mmap 직접 읽기 vs IPC** — 둘 다 IPC 를 기본으로 권함(키 입력당 1ms 를 아끼려고 Windows 매핑 파일 교체·SIGBUS 를 떠안을 이유가 없음). mmap 은 폴백에만.

### GPT Astra 검토 (v3)

사용자가 GPT Astra 로 받은 검토(v1 초안 기준으로 보임 — K=300·free 목록·prev_gen·30MB·오프셋 공용 지적은 v2 에서 이미 반영). 새로 반영한 것:

- **행 재사용 금지**: tombstone + 뒤에 붙이기 + 압축 시 `parent` 재구성(§3.2).
- **루트별 행 범위는 동적 갱신과 양립하지 않는다** → `root_id` 열(§3.2).
- **변경마다 테이블 전체 복제 금지** → 불변 기본 + 변경분 overlay(§3.2).
- 싼 점수는 **모든 후보**에 매긴다, 거르기는 Matcher 의 상위 집합(§3.3).
- **Dirty 큐**(Entry·Subtree·Root 격상), FSEvents `MustScanSubDirs`, 시작 시 "감시 먼저 등록 → 대조", 분할 전체 재스캔 안전망, 오프라인 루트, 신선도 두 등급(§3.6).
- **request_id 와 index_generation 분리**, UI 에서 20ms 기다리지 않기(§3.7).
- 호환성 정책 표(§3.13), 1·2·4·8 스레드·질의 종류별 벤치, 참조 구현 기반 차등 테스트, 상태 전이 테스트(§5).
- F0 완료 조건은 "50ms 안"이 아니라 "이전 결과가 남지 않음", 할당량 제거는 F3 검증 뒤 기본값(§4).
- `max_files` 를 넘으면 조용히 빼지 말고 "색인 불완전"을 보여 준다(§3.13).

그대로 둔 것: 전략 A(append-only + tombstone, 단순한 쪽으로 시작)를 권한 것과 v2 방향이 같다.

### GPT Astra 보안 검토 (v3.1)
